# Design Documents

Authoritative architecture and design decision documents. These govern implementation; when in conflict with other docs, these win.

- [codebase_map.md](codebase_map.md) — Visual reference for the structure of `eon_ecs` and `eon_engine`: module dependency graphs (per-package and cross-package), with regeneration instructions.
- [eon_engine_design.md](eon_engine_design.md) — Top-level design document for `eon_engine`: core philosophy, principles, module structure, and how the engine layer relates to `eon_ecs`.
- [eon_engine_query_design.md](eon_engine_query_design.md) — **SUPERSEDED** by `query_view_design.md`. Historical context for the earlier query API (`iter1..4`, `with_component`, `Archetype_backend`). Retained for design evolution reference only.
- [world_module_design.md](world_module_design.md) — World module design (ecs-016): `World.S` signature, concrete `World` module with per-world `Id_counter`, and `Sparse_set_backend.Make(W : World.S)` functor. Supersedes the `Archetype_backend` sections of the query design doc.
- [query_view_design.md](query_view_design.md) — Unified `iter` + typed `View` design: replaces the `iter1..4` arity-bound terminators with a single `iter` and a `View.get` accessor using OCaml 5.5 module-dependent functions (`View.get view (module Position) : Position.t`, no `Obj.magic` at call sites). Arbitrary component arity, no engine changes needed for five or more components. Supersedes the execution-function sections of `eon_engine_query_design.md`.
- [thread_safety_design.md](thread_safety_design.md) — Thread safety and parallel pipeline design: single-threaded-by-default philosophy, concurrency as the user's responsibility, `World.ro`/`World.rw` phantom capability types, and the reactive-system model where `update` is always read-only and `on_*` handlers are always sequential. Interacts with `world_module_design.md` and `query_view_design.md`.
- [parallel_pipeline_execution.md](parallel_pipeline_execution.md) — Implementation specification for the `eon_engine` parallel pipeline: `Dependency_graph` extraction, `Executor.S` interface, tagless execution algorithm (all phases dispatch via `Executor`; no `Read_only`/`Read_write` tags), capability downgrade (`World.readonly`) internal to `Pipeline.run` (preserving the `Progress`/`Loop` chain), `Eon_engine.Bus` with mutex-aware `Single_bus`/`Double_bus` (leaving `eon_ecs` buses untouched), and `Eon_engine.System` as the new public type. Translates the philosophy in `thread_safety_design.md` into concrete module shapes and functor signatures.
- [rendering_layer_design.md](rendering_layer_design.md) — Full specification of the rendering layer: `Render_stream`, `Render_stream_collector`, `Render_system`, `Rendering_backend`, polymorphic variant command extension, and frame flow. **IMPLEMENTED** (ecs-031).
- [data_service_plane_namespacing.md](data_service_plane_namespacing.md) — Design for namespacing the data-plane and service-plane at the `eon_engine` layer. Covers why the ECS core stays flat, world composition as the namespacing model, the `~ns` API, multi-world topologies, the `default_global_ns` convention, and the future `App.Make` functor.
- [world_manager_design.md](world_manager_design.md) — Stub design for a future `Worlds` module. Covers the problem (dangling references, transitions, enumeration), the reverse sparse-set index for O(R) cleanup, open design questions (naming, transition semantics, lifecycle hooks), and the future world execution pipeline — a `Pipeline`-like abstraction one level above systems. Not a near-term task.
- [grimdawn-style-multiplayer-distributed-buses.md](grimdawn-style-multiplayer-distributed-buses.md) — Exploratory design notes for a Grim Dawn-style listen server multiplayer model. Covers render graph compatibility with multiplayer, a wire-compatible pure OCaml ENet port, the distributed buses abstraction (location-transparent messaging), lockstep vs. listen server tradeoffs, and the one forward-looking constraint: all event/command payloads must be plain algebraic data. No implementation is planned.
- [math_types_design.md](math_types_design.md) — Design for the `eon_engine` math primitives: `Vec2`, `Rect`, and `Transform2D`. Concrete types only (no signatures or functors), all in a single `Math` module. Covers the full API surface for each type and what is deliberately excluded.
- [audio_system_design.md](audio_system_design.md) — Draft design for the `eon_engine` audio system: `Audio_backend.S` one-function contract (completing the PLATFORM trifecta), `Audio_command` vocabulary, `Audio_emitter`/`Audio_listener`/`Music_state` components, AudioSystem ro/rw split, voice budget prioritization, bus integration (Signals for one-shot SFX, components for spatial/looping), and recommendation to wrap miniaudio/raylib rather than implement from scratch.
- [input_system_design.md](input_system_design.md) — Full specification of the input system for `eon_engine`: `Input_backend.S` one-function contract, `Raw_input_frame.t` backend snapshot, input Exclusive system, mapping table (open polymorphic variant actions, world resource, EDN-loadable), hybrid bus integration (world resource for continuous state, local Signals for one-shot action slots), screen→world coordinate transform, click-to-move primary movement paradigm, and multiplayer boundary (input Signals local-only; distributed bus carries only resolved game commands).
